# 롤러 회전과 주행 오차의 원인 분석

분석일: 2026-11-05. 원본 USD SHA-256:
`567c4eb7681745698ab999c31ee81f2dc28dbb14598baf061bb19d6c88ada43c`.

## 결론

주요하게 확인된 문제는 **실제 롤러 축 배치와 제어·오도메트리 수식의 방향 정의가 반대**라는
점이다. 현재 모델은 yaw를 저항하는 기하학적 계수가 의도한 배치보다 약 11배 작다.
자유 롤러가 있는 상태에서 작은 접촉·구동 비대칭이 차체 회전으로 나타나기 쉬운 배치다.

롤러가 계속 회전하는 현상은 영향을 줄 수 있지만 회전 자체만으로 오류라고 판단하지 않는다.
원본과 같은 자유 회전 상태에서 축 방향만 맞춘 비교 모델은 정지 후 yaw가 크게 줄었고,
롤러가 여전히 회전해도 차체는 안정됐다. 롤러 잠금은 메카넘의 횡이동을 바꾸므로 해결책으로
채택하지 않았다.

이번 요청은 분석이므로 원본 URDF·USD, 기구학 및 구동 코드를 수정하지 않았다.
비교 시험의 변경은 별도 복사 장면의 메모리에만 적용했다.

## 기존 측정 재분석

이전 C++ 검증기의 1초 전진 + 2초 정지 관찰 자료에서:

- 전체 차체 yaw 약 4.91° 중 정지 구간의 추가 변화가 약 **4.22°**였다.
- 같은 정지 구간의 휠 회전 적분 yaw 변화는 약 **-0.033°**였다.
- 네 휠의 속도 목표는 모두 0인데 실제 관절 속도에는 진동이 남았다.

따라서 명령이 계속 들어오거나 단순 전진 적분 공식만의 문제라고 설명할 수 없다.
실제 차체 운동·롤러 접촉·휠 제동의 정합성을 확인해야 했다.

## 확인한 기하학 불일치

`generate_robot.py`는 휠 좌표계의 롤러 축을 다음처럼 생성한다.

```python
axis = (-sin(theta)*cos(angle), cos(theta)*cos(angle), hand*sin(angle))
```

휠은 로봇 +Y 축으로 회전하도록 Rx(-90°) 변환되어 있다. 명목 바닥 접촉 롤러
(theta=90°, wheel angle=0)의 긴 축을 로봇 좌표계로 변환하면 다음이 된다.

```text
a = [-cos(angle), hand*sin(angle), 0]
a_y / a_x = -hand  # angle=45°
```

반면 C++ 역기구학 및 전방 기구학은 다음 계수를 사용한다.

```text
wheel_speed = (vx - wz*y + hand*(vy + wz*x)) / radius
```

미끄러지지 않는 접촉점의 롤러 축 방향 속도를 0으로 두면 실제 형상에 대응하는 계수는
`a_y/a_x`여야 한다. 현재 모델의 그 값은 코드의 `hand`와 부호가 반대다.
URDF 수식만 추정한 것이 아니라 저장된 USD의 바닥 롤러 local Z축을 base_link 좌표계로
직접 변환해 확인했다.

| 바퀴 | USD의 실제 vy 계수 | 코드의 vy 계수 | 실제 명목 yaw 계수 m | 코드의 yaw 계수 m |
| --- | --- | --- | --- | --- |
| FL | +1 | -1 | -0.03 | -0.33 |
| FR | -1 | +1 | +0.03 | +0.33 |
| RL | -1 | +1 | -0.03 | -0.33 |
| RR | +1 | -1 | +0.03 | +0.33 |

실제 명목 yaw 계수는 track/2 - wheelbase/2 = 0.18 - 0.15 = **0.03 m** 크기다.
의도한 배치의 계수는 두 값의 합인 **0.33 m**다. 두 간격이 같으면 현재 배치의 명목
yaw 계수는 0이 되어 휠 회전만으로 yaw를 구속·관측하기 어려워진다.
실제 접촉점은 주행 중 변하므로 이 11배를 모든 시점의 실제 속도 배율로 해석하지 않는다.

소스 위치:

- `ros2_ws/src/amr_description/scripts/generate_robot.py`: 롤러 axis/pitch/yaw 생성.
- `ros2_ws/src/my_amr/src/mecanum_drive.cpp`: hand를 사용하는 역기구학.
- `ros2_ws/src/my_amr/src/mecanum_odometry.cpp`: 같은 정의를 사용하는 전방 기구학.
- `isaac_sim/mecanum.py`: 초기 CLI 경로도 같은 부호를 사용한다.

제어·오도메트리가 같은 수식을 공유하는 계산 시험만으로는 모델과의 불일치를 찾을 수 없다.
실제 URDF/USD 축과 수식의 정합성을 검사하는 회귀 시험이 필요하다.

## SDK 비교 시험

조건: 동일한 원본 USD 복사본, static 0.8/dynamic 0.6, 휠 drive damping 200,
토크 한계 8 N·m, 기본 물리 120 Hz. 2초 준비, 1초 명령, 3초 정지 관찰이다.
명령은 simulation time에 맞춰 0.5 m/s²로 상승시킨 0.1 m/s 목표를 사용했다.
SDK에서 네 휠 속도를 적용하고 PhysX 차체 pose 및 36개 관절 위치·속도·effort를 기록했다.

이 시험은 조건을 고정한 원인 분리용이며 기존 C++ 검증기와 명령 상승 구간·관찰 시간이
완전히 같지 않다. 아래 조건끼리 비교하며 이전 C++ 표의 수치와 직접 대체하지 않는다.
모든 사례는 각 360개의 앱 갱신 표본을 사용했다.

### 전진 후 회전

| 조건 | 정지 3초간 yaw 변화 | 마지막 1초 yaw 변화 | 해석 |
| --- | --- | --- | --- |
| 기존 자유 롤러, 120 Hz | 5.170° | 2.423° | 회전 지속 |
| 같은 조건 재시험 | 5.131° | 2.408° | 기존 현상 재현 |
| 주행 명령을 처음부터 0으로 유지 | 0° | 0° | 주행 이전에는 회전 없음 |
| 롤러의 회전 범위를 0으로 제한 | 0.0117° | 0° | 영향 확인용, 횡이동 특성이 달라짐 |
| 롤러에 시험용 작은 속도 저항 추가 | 3.333° | 1.438° | 감소하지만 지속, 근본 정합성은 그대로 |
| 롤러 축 방향만 수식과 맞춤, 자유 회전 유지 | **0.0259°** | **0.000013°** | 자유 회전 상태에서도 크게 개선 |

축 방향을 맞춘 모델의 마지막 1초에도 롤러 속도 RMS는 약 **0.310 rad/s**였다.
차체 yaw는 거의 변하지 않았다. 즉 “롤러가 돌면 차체가 계속 돌아야 한다”는 관계는 아니다.

롤러 저항 시험은 stiffness=0, targetVelocity=0, USD angular drive damping=0.0001,
maxForce=0.005 N·m를 추가한 진단 조건이다. 실측 베어링 저항으로 선정한 값이 아니며
제품 설정값으로 제안하지 않는다. 회전 제한 시험도 초기 관절 과도를 포함한다.

### 좌측 이동 명령의 방향 확인

같은 `+vy` 목표에 대응하는 휠 배열 `[-,+,+,-]`를 적용했다.

| 모델 | 1초 명령 구간의 실제 Y 변위 | 정지 3초간 추가 yaw |
| --- | --- | --- |
| 기존 모델 | **-83.56 mm**, 우측 | 3.260° |
| 축 방향을 맞춘 복사 모델 | **+82.33 mm**, 좌측 | 0.0155° |

명령 방향 자체가 반대로 나타나는 것으로 부호 불일치를 별도로 확인했다.

### 물리 주기를 높이는 것만으로는 해결이라고 판단할 수 없음

자유 롤러를 유지하고 물리 주기만 240 Hz로 바꾼 두 시험의 정지 yaw는 각각 **0.282°**와
**70.460°**였다. 결과 변동이 커서 240 Hz 변경만으로 개선된다고 결론내리지 않았다.
접촉·구동 모델의 수치 민감도가 있으며 최종 축 수정 후 반복 검증이 필요하다.

## 추가 후보: 원통 롤러 형상

현재 롤러는 배럴형 실제 휠을 단순 원통 8개로 근사했다. 중심 반경 59 mm, 롤러 반지름
16 mm, 길이 45 mm, 각도 45°를 사용한다.

이 이상적인 원통 배치의 수직 지지 외곽을 계산하면 휠 각도에 따라 **75.0~76.865 mm**로
변한다. 코드의 명목 휠 반지름은 75 mm다. 실제 비교 시험에서도 주행 중 차체 높이가 약
1.1~1.5 mm 변했다. 따라서 유효 반지름·접촉점 변화가 mm 수준 거리 오차와 진동에
기여할 가능성이 있다. 지지 외곽 계산이 실제 주행의 유효 반지름을 그대로 뜻하지는 않으며,
거리 오차 전체의 원인으로 확정하지 않았다.

## 롤러 구동 설정 확인

실행 시 configure_drives는 32개 롤러의 angular DriveAPI를 제거한다.
분석 시 활성 롤러 drive는 0개였고 native DOF properties에서도 예시 롤러의
stiffness=0, damping=0, maxEffort=0을 확인했다.

저장 USD에 남은 과거 drive 속성 문자열만 보고 롤러에 모터가 작동한다고 판단하면 안 된다.
현재 실행에서는 수동 조인트다. bearing 손실이 0이므로 비접촉 롤러가 계속 회전할 수는
있지만, 그 현상만으로 차체 drift를 진단하지 않는다.

## 권장 수정 순서

1. 현재 제어 수식의 방향 정의에 맞춰 롤러 축 배치를 수정하고 URDF와 USD를 함께 갱신한다.
   공통 handedness 값만 뒤집으면 생성기와 수식이 함께 뒤집혀 불일치가 남으므로 정의를
   일치시키는 수정이 필요하다. 이 변경은 아직 제품 모델에 반영하지 않았다.
2. 실제 축 기반 기구학 정합성 시험과 6방향 물리 주행·정지 시험을 수행한다.
3. 남은 거리 오차에 대해 원통 접촉 형상, 휠 반지름, 베어링 저항, 구동·물리 주기를 순서대로
   검토한다. 마찰이나 저항 수치만 올려 방향 정의 문제를 가리지 않는다.
